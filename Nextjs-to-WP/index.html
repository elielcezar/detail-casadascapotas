O WordPress vira só um painel

Ele não serve nenhuma página ao público. O Next.js lê o conteúdo durante o build e publica HTML estático. Quando o cliente clica em “Publicar”, um webhook dispara um novo build.

Sem servidor em produção

Nada de PHP nem banco de dados na frente do visitante. A superfície de ataque do site publicado é a de uma pasta de arquivos.

O WordPress mora onde quiser

Outro servidor, outro provedor, outro domínio. Ele só precisa responder HTTP no momento do build.

Queda não derruba o site

Se a API não responde, o build falha e nada é publicado. O site no ar fica exatamente como estava.

A decisão que vem primeiro

Antes de escrever uma linha, decida o que vai para o WordPress. É a decisão mais cara de reverter — e a que mais gente erra, porque a tentação é mandar tudo.

Conteúdo muito estruturado — tabelas técnicas, variantes de cor, flags de layout — vira repeater dentro de repeater no ACF. O resultado é uma interface pior que editar o arquivo TypeScript, que o cliente não entende e quebra sem perceber.

O critério não é “dá para fazer”. É com que frequência muda.

A pergunta que resolve os casos duvidosos: se o cliente preencher isso errado, o site fica feio ou quebra? Se quebra, fica no código.

O padrão de overlay

É o conceito central. Sem ele, “migrar para o WordPress” vira um salto sem rede.

src/data/*.ts define estrutura e valores padrão.

O WordPress fornece override apenas dos campos editáveis.

O casamento é por um id estável.

01

Falha de rede quebra o build. De propósito.

Nunca devolva lista vazia quando a API falhar. Em site estático, um build que passa com dados vazios publica páginas vazias e apaga o conteúdo do ar. Build quebrado se resolve em minutos; deploy vazio, não.

Não é teórico: durante esta implantação o WordPress ficou inalcançável por três minutos no meio de um deploy real. O build abortou, o deploy não aconteceu, o site ficou intacto.

02

Campo vazio usa o padrão do código.

Diferente de falha. É o que permite migrar uma seção por vez sem que as outras sumam, e o que protege o site quando alguém esvazia um campo por engano.

Diga ao cliente com estas palavras: apagar o texto no painel não apaga do site — volta o texto original.

03

Todo item editável precisa de um id estável.

E obrigatório no TypeScript, não opcional — assim o compilador acusa qualquer item que você esqueceu. Ao ligar 17 cards ao painel, foi o que garantiu que nenhum ficasse de fora. Um card esquecido cairia no texto padrão para sempre, em silêncio.

As seis fases

A ordem não é sugestão. Faça o WordPress inteiro antes de tocar no Next.js — sem CPTs e ACF prontos, o build falha e você perde horas diagnosticando o lado errado.

0

Pré-requisitos

Domínio, hospedagem, credenciais de deploy, licença ACF PRO (Repeater e Gallery são pagos) e — principalmente — quais pastas do servidor não podem ser apagadas.

Confira se o domínio de SEO no código é o real, e não um placeholder
1

WordPress

Subdomínio dedicado, permalinks “bonitos”, CPTs registrados em código num mu-plugin, grupos ACF exportados como JSON e versionados. Marque Show in REST em todo grupo.

Cada endpoint responde JSON no navegador antes de seguir
2

Camada de dados

Dois arquivos com papéis separados: um fala com a API, o outro decide o que sobrescreve o quê. User-Agent próprio, retentativas com espera crescente, nenhuma opção de cache no fetch.

Origem das imagens sai de variável de ambiente, não fixa no código
3

Seed

Script que lê os arquivos de dados e cria tudo via REST. Idempotente, com pausa entre uploads e um modo de simulação. Aqui foram 172 imagens e 33 posts em seis minutos — à mão seria um dia.

Rodar duas vezes não duplica nada
4

Componentes

Um por vez, do menos arriscado ao mais: galeria, equipe, contatos, cards, home. Componente de cliente não busca no build — recebe por prop de um componente de servidor.

Cada etapa é um commit que passa no build sozinho
5

Deploy

Workflow com fila de concorrência, timeout alto e lista de exclusão completa — a action apaga do servidor o que não existe no build.

Primeira execução em simulação, e o log precisa dizer “Deleting: 0 B”
6

Validação

Não confie no build passar. Se o valor no WordPress é igual ao padrão do código, um build verde não prova nada — pode estar lendo do código o tempo todo.

Altere no admin, rebuilde, confira o HTML gerado

O que muda conforme a hospedagem

Quatro coisas variam de provedor para provedor. Três delas são destrutivas quando você erra — e todas se conferem na Fase 0, não na hora do deploy.

visto marca o que foi verificado nesta implantação. O resto é comportamento conhecido dos painéis: liste o servidor antes de configurar, em vez de confiar na tabela.

1. Onde a conta de FTP cai

apaga arquivos

A action apaga do servidor tudo que não existe no build. Diretório de destino errado significa apagar o que estiver por perto — em cPanel, as contas de e-mail e os certificados do cliente.

PainelOnde caiO que mais mora lá
cPanelvisto/home/usuario/mail, ssl, logs, etc, public_html
hPanel/public_html, domains
Plesk/httpdocs, logs, anon_ftp
VPS própriovistoonde você definiro que você tiver posto

Em cPanel com domínio adicional, o site fica numa subpasta com o nome do domínio — não em public_html/. Foi o caso aqui.

2. .htaccess funciona ou é ignorado

Servidor.htaccessConsequência
Apachevistolêrewrite e CORS funcionam
LiteSpeedlêidem, mais o cache próprio
nginxvistoignora, em silêncioprecisa de server block, que você talvez não controle

Guias mandam resolver duas coisas por .htaccess: CORS no WordPress e um 403 no site estático. Nenhuma das duas é necessária. CORS não se aplica — a API só é lida no build, por Node. E o 403 some com trailingSlash: true, que faz o Next gerar rota/index.html em vez de rota.html ao lado da pasta. Funciona em qualquer servidor, sem configuração.

3. Protocolo, e se o certificado serve

credencial exposta

A action de deploy mais usada fala FTP e FTPS apenas. SFTP é protocolo sobre SSH e não é suportado — se o provedor só oferece SFTP, troque por rsync sobre SSH.

CenárioCertificadoFTPS valida?
Compartilhada, pelo domínio do clientevistocuringa do provedornão
Compartilhada, pelo hostname do servidoro mesmo curingasim
VPS com domínio própriovistoLet's Encrypt seusim

O hostname utilizável está no painel, em Informações gerais. Não adivinhe pelo DNS reverso: aqui o PTR devolveu um nome do provedor que resolvia para a Cloudflare, não para o servidor de FTP. Sem um nome que o certificado cubra, a escolha é entre FTP em texto puro e não ter deploy — decida e registre no workflow.

4. Que cache existe na frente

“Subi o arquivo e vejo o antigo” quase sempre é cache, não build. LiteSpeed em hospedagem compartilhada e Cloudflare quando o DNS passa por lá. Limpe antes de investigar o build — e confira que o Cache-Control do HTML não está em horas. Em site estático só os assets com hash podem ser cacheados agressivamente.

Armadilhas

Ler antes de “melhorar” qualquer coisa. Cada uma custou horas, e as três primeiras enganam porque não produzem erro nenhum.

O cache de fetch do Next publica conteúdo velho

O diretório de cache guarda as respostas do WordPress entre builds. O build roda, reporta sucesso e gera o site com o conteúdo anterior. No CI o diretório nasce vazio, então produção escapa por acidente — até alguém cachear .next/ para “acelerar o build”.

Sintoma: build verde, site desatualizado
Correção: apagar o cache num script prebuild

Retentativas brigam com o timeout de página

A escada de espera soma cerca de 52 segundos, mas o Next mata a geração de cada página aos 60 e recomeça. A última retentativa — a mais importante, porque é a que atravessa o bloqueio — nunca chega ao fim.

Aumente staticPageGenerationTimeout.
Não encurte a espera: ela é o mecanismo.

403 no webhook quase nunca é o token

O plugin de deploy vem com o repositório do projeto anterior como valor padrão. Com um token restrito ao repositório novo, o disparo vai para o lugar errado e o GitHub devolve um erro que parece de credencial.

Teste o mesmo token nos dois repositórios antes de regerar nada

A conta de FTP cai no home, não na raiz do site

Apontar o deploy para a barra faz a action apagar as pastas de e-mail, de certificados e de logs da hospedagem — do cliente, não suas.

Confira o diretório de destino antes do primeiro deploy automático

.well-known/ precisa estar na exclusão

É onde o Let's Encrypt valida a renovação do certificado. Apagar derruba o HTTPS algumas semanas depois — muito tempo depois de você ter esquecido do deploy.

A falha chega tarde demais para ser associada à causa

Campo obrigatório no ACF bloqueia update parcial

Um POST com um campo só é rejeitado exigindo todos os obrigatórios do grupo. O admin não sofre porque envia o formulário inteiro; quem quebra é script de seed e automação.

400 rest_invalid_param — a mensagem nomeia o campo

Repeater vazio volta como false

Não como lista vazia. Normalize antes de iterar, ou o primeiro .map() derruba o build na primeira seção que o cliente ainda não preencheu.

Aparece só quando alguém esvazia um campo — nunca no seu teste

Certificado FTPS não cobre o domínio do cliente

Em hospedagem compartilhada o certificado é do provedor. Conectar pelo domínio do cliente ou pelo IP falha na validação. O nome utilizável está no painel da hospedagem.

Sem ele: FTP em texto puro ou nada. Decida e registre no workflow.

Um salvamento dispara vários hooks

O editor de blocos salva mais de uma vez, e um post publicado aciona dois hooks diferentes. Sem debounce no plugin, uma edição vira quatro deploys concorrentes.

Que então se derrubam no FTP, um ao outro

Ordenar por menu_order exige suporte declarado

O CPT precisa declarar page-attributes. Sem isso a REST API rejeita o parâmetro e o build cai — mas só nos tipos que o site ordena.

400 em orderby=menu_order

cache: "no-store" gera páginas 404

Com export estático, o Next entende que a rota é dinâmica e não consegue pré-renderizar. Sem opções de cache, o fetch roda uma vez no build — que é exatamente o desejado.

A correção parece uma regressão, mas é o comportamento correto

O WordPress devolve entidades HTML

Títulos chegam com aspas curvas e traços codificados. Decodifique todo texto que não for renderizado como HTML, ou eles aparecem crus na página.

&#8220; no lugar das aspas

Antes de entregar

As três marcadas são as que provam a integração. O resto confirma que nada quebrou no caminho.

  • Alterar um valor no admin muda o HTML gerado
  • Build apontado para host inexistente falha, em vez de publicar vazio
  • Deploy em simulação reporta Deleting: 0 B
  • A chave acf vem com a forma que o TypeScript espera
  • orderby=menu_order responde 200 nos CPTs ordenados
  • Um trecho real do conteúdo aparece no HTML gerado
  • O que existe no servidor e não vem do build está na lista de exclusão
  • Publicar no WordPress dispara o workflow sozinho
  • A mudança aparece no site em 3 a 5 minutos
  • Pastas externas continuam no servidor depois do deploy
  • Cache do servidor limpo e testado em aba anônima
  • Senha de FTP e token trocados ao entregar o painel
  • Cliente avisado: renomear página é seguro, excluir e recriar quebra
